Phần 1: Các Câu Lệnh Thao Tác Với Tệp Tin Trong Linux VPS

Nền tảng quản trị hệ điều hành máy chủ Linux (Ubuntu, Debian, CentOS, RHEL)

📁 1.1 Bản Chất Cây Thư Mục Linux (Filesystem Hierarchy)

Không giống Windows phân chia ổ đĩa thành C:\, D:\, trong Linux tất cả mọi thứ đều là tệp tin (Everything is a file) và bắt đầu từ một thư mục gốc duy nhất là thư mục root (/).

Sơ đồ: Cấu trúc thư mục cốt lõi trên máy chủ Linux VPS mà kỹ sư DevOps cần nắm vững
💡
Phân biệt đường dẫn Tuyệt đối vs Tương đối:
  • Đường dẫn tuyệt đối (Absolute Path): Luôn bắt đầu bằng dấu gạch chéo /, ví dụ /var/www/html/index.html. Luôn chỉ đúng 1 nơi dù bạn đang đứng ở đâu.
  • Đường dẫn tương đối (Relative Path): Bắt đầu từ vị trí hiện tại của bạn, dùng ./ (thư mục này) hoặc ../ (lùi ra thư mục cha). Ví dụ ../nginx/nginx.conf.

🧭 1.2 Lệnh Định Hướng & Xem Thông Tin (pwd, cd, ls)

Lệnh Cú pháp mẫu Ý nghĩa & Các cờ (Flags) quan trọng Ứng dụng DevOps thực tế
pwd pwd Print Working Directory: In đường dẫn thư mục hiện hành đang đứng. Xác định bạn đang đứng ở đâu trước khi chạy lệnh xóa hoặc deploy.
cd cd /var/www/html
cd ..
cd ~
cd - 		Change Directory: Chuyển thư mục công tác.
• cd .. : Lùi về thư mục cha 1 cấp.
• cd ~ : Về thư mục Home cá nhân (/root hoặc /home/user).
• cd - : Quay lại thư mục vừa đứng trước đó (cực tiện!). 		Di chuyển nhanh chóng giữa thư mục cấu hình Nginx và thư mục mã nguồn.
ls ls -la
ls -lh
ls -ltr 		List: Liệt kê danh sách tệp tin & thư mục.
• -a: Hiện tất cả, bao gồm cả tệp ẩn (bắt đầu bằng dấu chấm như .env, .git).
• -l: Xem dạng danh sách dài (quyền, owner, kích thước, thời gian).
• -h: Human-readable (hiển thị KB, MB, GB thay vì byte).
• -t & -r: Sắp xếp theo thời gian sửa đổi (mới nhất lên trên / đảo ngược). 		Kiểm tra file cấu hình môi trường ẩn .env hoặc kiểm tra file log mới nhất vừa sinh ra.
Terminal: Ví dụ chạy ls -lah
ls -lah /var/www/html # Kết quả mẫu: # drwxr-xr-x 2 root root 4.0K Oct 6 08:30 . # drwxr-xr-x 3 root root 4.0K Oct 6 08:29 .. # -rw-r--r-- 1 www-data www-data 612 Oct 6 08:30 index.html # -rw------- 1 www-data www-data 145 Oct 6 08:35 .env

✍️ 1.3 Tạo, Đọc & Chỉnh Sửa Tệp Tin (touch, mkdir, cat, less, tail, nano, vim)

Trên máy chủ VPS không có giao diện đồ họa chuột phải, mọi thao tác tạo và đọc file đều thông qua dòng lệnh:

Lệnh Cú pháp mẫu Mô tả chi tiết & Cờ thông dụng
touch touch app.js index.html Tạo một hoặc nhiều tệp tin rỗng mới. Nếu tệp đã có sẵn, cập nhật thời gian sửa đổi (timestamp) mà không làm mất nội dung.
mkdir mkdir -p /var/www/project/assets/css Make Directory: Tạo thư mục mới.
• Cờ -p (parents): Tự động tạo toàn bộ chuỗi thư mục cha nếu chúng chưa tồn tại. Không báo lỗi nếu thư mục đã có.
cat cat /etc/nginx/nginx.conf In toàn bộ nội dung của tệp ra thẳng màn hình terminal. Thích hợp cho file ngắn (dưới 50 dòng).
less less /var/log/syslog Xem tệp dài có phân trang: cuộn bằng phím mũi tên hoặc Space, tìm kiếm bằng /từ_khóa, nhấn q để thoát.
head / tail head -n 20 error.log
tail -n 30 error.log
tail -f /var/log/nginx/access.log 		• head -n 20: Xem 20 dòng đầu tiên.
• tail -n 30: Xem 30 dòng cuối cùng.
• -f (follow): CỰC KỲ QUAN TRỌNG trong DevOps: Giữ mở và theo dõi dòng log mới nhất được ghi vào theo thời gian thực (nhấn Ctrl + C để dừng).
nano nano /etc/nginx/nginx.conf Trình soạn thảo văn bản đơn giản, thân thiện: Lưu file nhấn Ctrl + O rồi Enter, thoát nhấn Ctrl + X.
vim vim index.html Trình soạn thảo chuyên nghiệp mặc định trên mọi Linux Server:
• Nhấn phím i để vào chế độ gõ (Insert mode).
• Nhấn phím Esc để về Normal mode.
• Gõ :wq rồi Enter: Lưu và thoát.
• Gõ :q! rồi Enter: Thoát mà KHÔNG lưu thay đổi.

📦 1.4 Sao Chép, Di Chuyển, Đổi Tên & Xóa (cp, mv, rm)

Terminal: Các thao tác cp, mv, rm
# 1. Sao chép tệp tin đơn lẻ: cp [nguồn] [đích] cp index.html index.html.bak # 2. Sao chép cả THƯ MỤC (Bắt buộc dùng cờ -r hoặc -R: recursive) cp -r /my-app /var/www/my-app # 3. Đổi tên tệp (Linux coi đổi tên là di chuyển đến tên mới) mv old-config.conf new-config.conf # 4. Di chuyển tệp tin sang thư mục khác mv main.js /var/www/html/js/ # 5. Xóa tệp tin đơn lẻ rm temp.txt # 6. Xóa thư mục có chứa dữ liệu (cờ -r: đệ quy, cờ -f: ép buộc, không hỏi xác nhận) rm -rf /var/www/old-website
⚠️
CẢNH BÁO AN TOÀN DEVOPS TUYỆT ĐỐI:
Lệnh rm -rf trên Linux xóa vĩnh viễn và KHÔNG CÓ THÙNG RÁC (RECYCLE BIN)! Không bao giờ chạy lệnh rm -rf /* hoặc rm -rf / vì nó sẽ xóa sạch toàn bộ hệ điều hành VPS ngay lập tức. Luôn kiểm tra kỹ đường dẫn bằng pwd hoặc ls trước khi enter!

🔍 1.5 Tìm Kiếm & Lọc Dữ Liệu (find, grep, Pipe |)

Kỹ năng tìm file và tìm dòng văn bản trong code/config là kỹ năng phỏng vấn DevOps cốt lõi:

Terminal: find & grep thực chiến
# A. Tìm kiếm FILE / THƯ MỤC theo tên bằng FIND: # Tìm mọi file kết thúc bằng .conf trong thư mục /etc: find /etc -type f -name "*.conf" # Tìm file có dung lượng lớn hơn 100MB để dọn dẹp ổ đĩa: find /var/log -type f -size +100M # B. Tìm kiếm CHUỖI VĂN BẢN bên trong tệp tin bằng GREP: # -r: đệ quy thư mục con, -n: in số dòng, -i: không phân biệt hoa thường grep -rni "server_name" /etc/nginx/ # C. Kết hợp đường ống PIPE (|) để lọc kết quả đầu ra: # Xem danh sách tiến trình đang chạy và chỉ lọc tiến trình Nginx: ps aux | grep "nginx" # Đếm số lượng request có mã lỗi 404 trong log: cat /var/log/nginx/access.log | grep " 404 " | wc -l

🔐 1.6 Phân Quyền & Sở Hữu Tệp (chmod, chown - Trọng Tâm Bài Thi)

Mỗi tệp tin và thư mục trong Linux đều thuộc quyền quản lý của 3 đối tượng người dùng:

1. Owner (u): Người tạo ra tệp (Chủ sở hữu).
2. Group (g): Nhóm người dùng có chung quyền.
3. Others (o): Bất kỳ ai khác trên hệ thống / người truy cập web.

Ý nghĩa chuỗi 10 ký tự quyền hạn (Ví dụ: -rwxr-xr--)

- rwx r-x r-- | | | | Loại tệp Owner (Chủ) Group (Nhóm) Others (Người khác) (-: file, (Read, Write, (Read, Chạy, (Chỉ đọc) d: folder) Execute) Không ghi)

Quy đổi hệ nhị phân sang số Bát Phân (Octal Number):

  • r (Read - Đọc): Trọng số = 4
  • w (Write - Ghi / Sửa / Xóa): Trọng số = 2
  • x (Execute - Thực thi file nhị phân hoặc vào thư mục): Trọng số = 1
  • - (Không có quyền): Trọng số = 0
Mã số Ký hiệu Mô tả chi tiết Khi nào sử dụng trong thực tế?
755 rwxr-xr-x Owner có toàn quyền (7), Group và Others chỉ có quyền Đọc & Thực thi (5). Quyền chuẩn cho thư mục web (/var/www/html) và các file Bash Script.
644 rw-r--r-- Owner có quyền Đọc & Ghi (6), Group và Others chỉ có quyền Đọc (4). Quyền chuẩn cho các file mã nguồn tĩnh (index.html, style.css, hình ảnh).
777 rwxrwxrwx Ai cũng có toàn quyền đọc, sửa, xóa và chạy chương trình. Cực kỳ nguy hiểm! Tuyệt đối không dùng trên Production vì hacker có thể chèn webshell.
400 / 600 r-------- / rw------- Chỉ duy nhất Owner được đọc (400) hoặc đọc/ghi (600), người khác bị cấm tuyệt đối. Bắt buộc cho SSH Private Key (id_rsa) và file bí mật (.env).
Terminal: Lệnh chmod & chown
# 1. Đổi quyền (CHMOD: Change Mode) chmod 755 /var/www/html chmod 644 /var/www/html/index.html chmod +x deploy.sh # Cấp thêm quyền thực thi (+x) cho script # 2. Đổi chủ sở hữu (CHOWN: Change Owner) # Cú pháp: chown -R [user]:[group] [thư mục] chown -R www-data:www-data /var/www/html # Giải thích: Gán quyền sở hữu cho user hệ thống www-data (user mà Nginx sử dụng để đọc web)

🗜️ 1.7 Nén, Giải Nén, Dung Lượng Ổ Đĩa & Symbolic Link

Terminal: tar, df, du, ln -s
# 1. Nén thư mục thành file .tar.gz (c: create, z: gzip, v: verbose, f: file) tar -czvf backup-website.tar.gz /var/www/html # 2. Giải nén file .tar.gz vào thư mục đích (x: extract) tar -xzvf backup-website.tar.gz -C /var/www/restored/ # 3. Kiểm tra dung lượng toàn bộ ổ cứng VPS (df: Disk Free, -h: Human-readable) df -h # 4. Kiểm tra dung lượng chi tiết của từng thư mục để tìm file rác (du: Disk Usage) du -sh /var/log/* # 5. Tạo Symbolic Link (Liên kết mềm - Phím tắt trỏ đến file thực tế) # Cực kỳ quan trọng để kích hoạt site trong Nginx: ln -s /etc/nginx/sites-available/mysite.conf /etc/nginx/sites-enabled/

Phần 2: Các Câu Lệnh Thao Tác Với Git Flow

Mô hình phân nhánh chuyên nghiệp tiêu chuẩn ngành cho nhóm phát triển và CI/CD

💡 2.1 Bản Chất Git Flow Là Gì? Tại Sao Cần Git Flow?

Git Flow là một mô hình phân nhánh (Branching Model) được tác giả Vincent Driessen công bố năm 2010. Nó thiết lập một bộ quy tắc nghiêm ngặt về cách tổ chức và quản lý các nhánh trong kho mã nguồn Git cho dự án phần mềm có lịch trình phát hành (Scheduled Releases).

Vấn đề khi KHÔNG dùng Git Flow:

Mọi người commit chung lên main hoặc phân nhánh tùy tiện. Code đang dở dang bị đẩy lên Production gây sập app, khi có lỗi khẩn cấp không biết sửa từ đâu mà không kéo theo code chưa kiểm thử.

Lợi ích khi ÁP DỤNG Git Flow:

Tách biệt hoàn toàn giữa code đã phát hành (Production), code đang tích hợp (Development), và code đang làm tính năng. Dễ dàng tung bản vá nóng (Hotfix) trong 5 phút mà không đụng chạm đến code đang phát triển.

Sơ đồ: Mô hình 5 loại nhánh trong Git Flow và luồng tích hợp code chuẩn quốc tế

🌳 2.2 & 2.3 Phân Loại 5 Nhánh Trong Git Flow

Tên nhánh Vòng đời Tách từ (Branch from) Merge quay về Mục đích sử dụng chính
main / master Vĩnh viễn Khởi tạo dự án Không (chỉ nhận merge) Chứa mã nguồn ổn định nhất đang chạy thực tế trên máy chủ Production. Mỗi commit tại đây luôn có một Git Tag (v1.0.0, v1.1.0).
develop Vĩnh viễn Tách từ main Không (chỉ nhận merge) Nhánh tích hợp trung tâm. Chứa tất cả mã nguồn mới nhất đã hoàn thành để chuẩn bị cho đợt phát hành kế tiếp.
feature/* Tạm thời develop develop Phát triển một tính năng cụ thể (VD: feature/login, feature/cart). Sau khi xong và test qua, merge lại vào develop rồi xóa nhánh.
release/* Tạm thời develop CẢ main VÀ develop Chuẩn bị phát hành phiên bản mới (VD: release/v1.0.0). Đóng băng tính năng mới, chỉ fix lỗi nhỏ cuối cùng, cập nhật số version và tài liệu.
hotfix/* Tạm thời main CẢ main VÀ develop Vá lỗi khẩn cấp xảy ra trực tiếp trên Production (VD: hotfix/v1.0.1). Sau khi sửa xong, merge vào main (gắn tag mới) và merge ngược về develop để develop cũng có bản vá.

⚡ 2.4 Quy Trình Lệnh Git Flow Chi Tiết Bằng Câu Lệnh Thực Chiến

Dưới đây là 2 cách thực thi Git Flow: Bằng các câu lệnh Git Thuần Túy (Pure Git) (cách hay ra thi nhất) và dùng tiện ích git-flow CLI.

Bước 1: Khởi tạo kho mã nguồn & Nhánh Develop

Tạo nhánh develop từ main lần đầu tiên.

Terminal: Khởi tạo
# Cách 1: Git Thuần Túy git checkout -b develop main git push -u origin develop # Cách 2: Bằng git-flow tool (Tự động hỏi đặt tên nhánh mặc định) git flow init

Bước 2: Phát triển Tính Năng Mới (Feature)

Ví dụ phát triển tính năng xác thực người dùng feature/auth.

Terminal: Feature Branch
# 1. Tách nhánh feature từ develop: git checkout develop git pull origin develop git checkout -b feature/auth develop # 2. Lập trình và commit: git add . git commit -m "feat: hoàn thành module đăng nhập người dùng" # 3. Hoàn thành feature và merge lại vào develop: git checkout develop git merge --no-ff feature/auth git push origin develop # 4. Xóa nhánh feature cục bộ sau khi đã merge thành công: git branch -d feature/auth
💡
Tại sao BẮT BUỘC dùng git merge --no-ff?
Cờ --no-ff (No Fast-Forward) yêu cầu Git luôn luôn tạo ra một Commit Merge riêng biệt ngay cả khi có thể tua nhanh. Điều này giúp toàn bộ nhóm commit của tính năng được gói gọn, dễ truy vết lịch sử hoặc revert nguyên cả cụm tính năng khi gặp lỗi.

Bước 3: Chuẩn bị Bản Phát Hành (Release)

Khi develop đã tích lũy đủ tính năng để phát hành phiên bản v1.0.0.

Terminal: Release Branch
# 1. Tách nhánh release từ develop: git checkout -b release/v1.0.0 develop # 2. Fix lỗi nhỏ, sửa file package.json / version, commit: git commit -am "bump version to v1.0.0 and polish docs" # 3. Merge vào nhánh MAIN và gắn TAG phiên bản: git checkout main git merge --no-ff release/v1.0.0 git tag -a v1.0.0 -m "Release phiên bản chính thức v1.0.0" # 4. Merge ngược lại vào DEVELOP (để đồng bộ các bản vá trong lúc release): git checkout develop git merge --no-ff release/v1.0.0 # 5. Xóa nhánh release và đẩy tags lên remote: git branch -d release/v1.0.0 git push origin main --tags git push origin develop

Bước 4: Xử lý Sự Cố Khẩn Cấp Trên Production (Hotfix)

Phát hiện lỗi nghiêm trọng trên máy chủ thật đang chạy v1.0.0.

Terminal: Hotfix Branch
# 1. Tách nhánh hotfix trực tiếp từ MAIN: git checkout -b hotfix/v1.0.1 main # 2. Vá lỗi và commit: git commit -am "fix: vá lỗi bảo mật SQL Injection khẩn cấp" # 3. Merge vào MAIN và gắn Tag phiên bản mới v1.0.1: git checkout main git merge --no-ff hotfix/v1.0.1 git tag -a v1.0.1 -m "Hotfix v1.0.1 khẩn cấp" # 4. BẮT BUỘC: Merge ngược lại vào DEVELOP (tránh bị mất bản vá trong các lần release sau): git checkout develop git merge --no-ff hotfix/v1.0.1 # 5. Xóa nhánh hotfix và đẩy lên remote: git branch -d hotfix/v1.0.1 git push origin main --tags git push origin develop

📋 2.5 Các Lệnh Git Bổ Trợ Đắc Lực & Quy Tắc Vàng

Terminal: Lệnh Git hữu ích thường dùng trong Git Flow
# Xem cây lịch sử commit trực quan dạng đồ thị ngay trên terminal: git log --oneline --graph --all --decorate # Cất tạm code đang làm dở khi phải chuyển gấp sang nhánh hotfix: git stash git stash pop # Lấy lại code sau khi sửa hotfix xong # Xem danh sách tất cả các nhánh (cả local và remote): git branch -a # Xóa nhánh trên remote repository: git push origin --delete feature/auth
📌
3 QUY TẮC VÀNG TRONG BÀI THI & DỰ ÁN DEVOPS:
  1. Không bao giờ commit trực tiếp lên main (Trừ khi merge từ release hoặc hotfix).
  2. Hotfix luôn phải merge vào CẢ HAI nhánh: main VÀ develop. Nếu quên merge về develop, lần release sau sẽ làm tái diễn lỗi cũ!
  3. Luôn kéo code mới nhất (git pull) trước khi tạo nhánh mới hoặc trước khi merge để hạn chế tối đa xung đột (Merge Conflict).

⚔️ 2.6 Hướng Dẫn Xử Lý Xung Đột (Merge Conflict) Thực Chiến

Xung đột mã nguồn (Merge Conflict) xảy ra khi hai nhánh cùng thay đổi trên cùng một dòng trong cùng một tệp tin (hoặc một bên sửa nội dung, một bên xóa tệp). Khi merge vào nhau (ví dụ: merge feature/login vào develop hoặc merge hotfix vào main), Git không thể tự đoán code của ai là chính xác nên sẽ dừng tiến trình và yêu cầu bạn can thiệp thủ công.

1. Dấu hiệu nhận biết khi bị Merge Conflict:

Khi chạy lệnh merge, terminal sẽ thông báo lỗi và trạng thái nhánh lập tức chuyển sang chế độ MERGING:

Terminal: Thông báo xung đột từ Git
git checkout develop git merge --no-ff feature/header # Git thông báo lỗi xung đột: Auto-merging index.html CONFLICT (content): Merge conflict in index.html Automatic merge failed; fix conflicts and then commit the result. # Trạng thái dấu nhắc terminal sẽ đổi thành: (develop|MERGING)

2. Cấu trúc đánh dấu Conflict Marker chuẩn trong file code:

Mở file bị xung đột (ví dụ: nano index.html), bạn sẽ thấy Git tự động đánh dấu 3 vùng bằng các ký hiệu đặc biệt:

Bên trong file index.html bị Conflict
<<<<<<< HEAD <title>Hệ Thống Đào Tạo Công Nghệ PTIT</title> # (Đoạn mã hiện tại đang nằm trên nhánh develop mà bạn đang đứng) ======= <title>Học Viện Công Nghệ Bưu Chính Viễn Thông - DevOps</title> # (Đoạn mã mới từ nhánh feature/header đang được kéo vào merge) >>>>>>> feature/header

3. Quy trình 5 Bước Giải Quyết Conflict Chuẩn DevOps:

Bước 1: Xác định danh sách các file đang bị xung đột

Chạy git status để kiểm tra danh sách tệp chưa được hợp nhất (Unmerged paths):

Terminal
git status # Kết quả hiển thị: # Unmerged paths: # both modified: index.html
Bước 2: Mở file và lựa chọn phương án giải quyết

Mở tệp tin bằng nano index.html, vim index.html hoặc VS Code. Trao đổi với người viết đoạn code còn lại và đưa ra quyết định:
• Giữ lại code HEAD: Lấy code của nhánh hiện tại.
• Lấy code Feature: Ghi đè bằng code mới của tính năng.
• Kết hợp cả 2: Viết lại một đoạn mã thống nhất giữ được logic của cả 2 bên.

Bước 3: Xóa bỏ hoàn toàn các ký hiệu đánh dấu Conflict

QUY TẮC BẮT BUỘC: Phải xóa sạch các dòng <<<<<<< HEAD, =======, và >>>>>>> branch_name. Chỉ để lại mã nguồn HTML/CSS hoàn chỉnh, sau đó lưu tệp lại.

Bước 4: Đánh dấu tệp tin đã được giải quyết (Mark as Resolved)

Dùng lệnh git add để thông báo với Git rằng tệp đã được sửa xong:

Terminal
git add index.html
Bước 5: Commit hoàn tất tiến trình Merge

Tạo một commit merge để kết thúc quá trình giải quyết xung đột:

Terminal
git commit -m "merge: giải quyết xung đột index.html giữa develop và feature/header" git push origin develop # Trạng thái terminal trở lại bình thường (develop) sạch sẽ!
💡
LỆNH "CỨU CÁNH" KHI BỊ RỐI: git merge --abort
Nếu trong lúc xử lý xung đột bạn thấy quá phức tạp, chưa chắc chắn hoặc sợ làm mất mã nguồn quan trọng, hãy gõ ngay lệnh:
git merge --abort
Lệnh này sẽ lập tức dừng merge và khôi phục kho mã nguồn quay về nguyên vẹn 100% như thời điểm trước khi bạn bấm lệnh merge, hoàn toàn không gây mất mát dữ liệu!
⚡

Phần 3: Nginx & Quy Trình Deploy Ứng Dụng HTML

Kiến trúc Web Server, cấu hình Virtual Host và triển khai ứng dụng tĩnh thực chiến

🌐 3.1 Nginx Là Gì? Tại Sao Nginx Lại Thống Trị DevOps?

Nginx (phát âm là "Engine-X") là một phần mềm mã nguồn mở nổi tiếng đóng vai trò là:

1. Web Server Tốc Độ Cao:

Phục vụ file tĩnh (HTML, CSS, JS, Image) cực kỳ nhanh với mức tiêu thụ RAM tối thiểu.

2. Reverse Proxy:

Đứng trước che giấu Backend (NodeJS, Java Spring, Python Django), chuyển tiếp request an toàn.

3. Load Balancer:

Cân bằng tải phân phối lượng truy cập khổng lồ giữa nhiều server backend khác nhau.

Bí quyết hiệu năng của Nginx: Thay vì tạo một luồng (thread) mới cho mỗi khách hàng như Apache (dễ gây cạn kiệt RAM khi có 10.000 kết nối - vấn đề C10K), Nginx sử dụng kiến trúc hướng sự kiện bất đồng bộ (Asynchronous Event-driven Architecture), cho phép một tiến trình đơn (Worker Process) xử lý đồng thời hàng nghìn request mà bộ nhớ chỉ tốn vài chục Megabytes.

Sơ đồ: Luồng xử lý một Request HTTP trang tĩnh HTML thông qua Nginx

⚙️ 3.2 Cài Đặt & Các Lệnh Quản Lý Nginx (systemctl, nginx -t)

Terminal: Cài đặt và quản lý Nginx trên Ubuntu/Debian
# 1. Cập nhật danh sách gói và cài đặt Nginx: sudo apt update sudo apt install -y nginx # 2. KIỂM TRA CÚ PHÁP CẤU HÌNH (BẮT BUỘC CHẠY TRƯỚC MỌI LẦN RELOAD): sudo nginx -t # Nếu ra "syntax is ok" và "test is successful" mới được tiếp tục! # 3. Nạp lại cấu hình mượt mà KHÔNG làm gián đoạn người dùng (Zero Downtime): sudo systemctl reload nginx # 4. Kiểm tra trạng thái hoạt động: sudo systemctl status nginx # 5. Các lệnh vòng đời dịch vụ khác: sudo systemctl start nginx # Khởi động dịch vụ sudo systemctl stop nginx # Dừng dịch vụ sudo systemctl restart nginx # Khởi động lại toàn bộ (ngắt kết nối) sudo systemctl enable nginx # Cho phép tự khởi động cùng VPS khi boot
💡
So sánh systemctl restart vs systemctl reload:

• restart: Tắt hoàn toàn tiến trình master và các worker rồi bật lại từ đầu. Gây mất kết nối tạm thời đối với khách hàng đang tải trang.
• reload: Giữ nguyên tiến trình master, kiểm tra config và khởi tạo các worker mới theo cấu hình mới, sau đó từ từ đóng các worker cũ khi họ phục vụ xong. Luôn ưu tiên dùng reload trên Production!

📂 3.3 Cấu Trúc Thư Mục Nginx Cốt Lõi Trên VPS

Đường dẫn Loại Chức năng & Ý nghĩa
/etc/nginx/nginx.conf File cấu hình File cấu hình tổng thể (Global Configuration) điều khiển số lượng worker, luồng sự kiện, kiểu MIME và nạp các site con.
/etc/nginx/sites-available/ Thư mục Nơi lưu trữ file cấu hình của tất cả các trang web có sẵn (nhưng chưa kích hoạt chạy).
/etc/nginx/sites-enabled/ Thư mục Nơi chứa các liên kết mềm (Symbolic Link) trỏ từ sites-available sang. Chỉ những file có mặt ở đây mới được Nginx nạp chạy!
/var/www/html/ Thư mục Thư mục gốc mặc định chứa trang chào mừng Nginx (chứa index.nginx-debian.html).
/var/log/nginx/access.log File Log Ghi lại mọi lượt truy cập của người dùng (Địa chỉ IP, thời gian, URL, mã phản hồi HTTP, trình duyệt).
/var/log/nginx/error.log File Log Ghi lại mọi lỗi phát sinh (Lỗi cú pháp, quyền truy cập 403, file không tồn tại 404, sập upstream 502).

📝 3.4 Cấu Hình Server Block (Virtual Host) Chi Tiết Cho Ứng Dụng HTML

Mỗi website tĩnh được định nghĩa bằng một khối lệnh server { ... }. Dưới đây là file cấu hình chuẩn mẫu và phân tích cặn kẽ từng dòng:

/etc/nginx/sites-available/my-static-web.conf
server { # 1. Cổng lắng nghe (80 là cổng chuẩn HTTP mặc định) listen 80; listen [::]:80; # Hỗ trợ IPv6 # 2. Tên miền hoặc địa chỉ IP của VPS server_name demo-devops.com www.demo-devops.com 192.168.1.100; # 3. Đường dẫn tuyệt đối đến thư mục chứa mã nguồn HTML/CSS root /var/www/my-static-web; # 4. Tệp tin mặc định phục vụ khi người dùng vào trang chủ index index.html index.htm; # 5. Định tuyến xử lý request location / { # Thử tìm file theo đúng URL ($uri), nếu không có thử tìm thư mục ($uri/), # Nếu vẫn không thấy thì trả về lỗi 404 (hoặc trỏ về /index.html nếu là SPA React/Vue) try_files $uri $uri/ =404; } # 6. Tối ưu bộ nhớ Cache cho các tệp tĩnh (CSS, JS, Ảnh) location ~* \.(css|js|jpg|jpeg|png|gif|ico|svg|woff2)$ { expires 30d; add_header Cache-Control "public, no-transform"; } # 7. Trang thông báo lỗi tùy biến (Custom Error Page) error_page 404 /404.html; location = /404.html { internal; } }
Chỉ thị (Directive) Ý nghĩa cốt lõi cần nhớ khi làm bài
listen Khai báo cổng TCP mà Nginx tiếp nhận kết nối (HTTP dùng cổng 80, HTTPS dùng cổng 443).
server_name Định danh trang web: domain hoặc IP. Nginx so khớp trường Host trong header request với directive này để biết phải phục vụ website nào.
root Thư mục chứa mã nguồn trên ổ cứng VPS. Nếu request là /style.css, Nginx tìm ở /var/www/my-static-web/style.css.
index Tên file hiển thị đầu tiên khi client không chỉ định tên file cụ thể.
try_files $uri $uri/ =404 Cực kỳ quan trọng: Giúp kiểm tra xem file có tồn tại trên đĩa không trước khi trả về mã lỗi.

🚀 3.5 Quy Trình 8 Bước Deploy File HTML Có Sẵn Trên VPS Lên Nginx Chuẩn A-Z

Trong thực tế quản trị DevOps hoặc làm bài thi môn học, bạn thường đã có sẵn thư mục chứa các file mã nguồn tĩnh (ví dụ: index.html, style.css) nằm sẵn trong thư mục người dùng trên máy chủ VPS (ví dụ tại ~/my-website/ hoặc vừa tạo trực tiếp bằng terminal). Dưới đây là quy trình từng bước đưa file có sẵn này lên chạy chính thức trên Nginx Web Server:

Bước 1: Cài đặt và kích hoạt dịch vụ Nginx trên VPS

Kết nối SSH vào VPS bằng PuTTY/Terminal: ssh user@your_vps_ip và cài đặt Nginx:

Bash
sudo apt update && sudo apt install -y nginx sudo systemctl enable nginx sudo systemctl status nginx

Bước 2: Tạo thư mục Web Root trên Nginx

Tạo thư mục dành riêng để chứa mã nguồn website tĩnh tại phân vùng chuẩn /var/www/:

Bash
sudo mkdir -p /var/www/my-static-web

Bước 3: Đưa file HTML có sẵn trên VPS vào thư mục Web Root

Tùy thuộc vào việc file HTML của bạn đang ở đâu trên VPS, chọn 1 trong 2 cách sau:

Bash: Đưa file HTML có sẵn vào thư mục web
# CÁCH 1: Nếu bạn đã có sẵn thư mục chứa file HTML (ví dụ tại ~/my-website/): # Dùng lệnh cp -r để sao chép toàn bộ file vào thư mục web root: sudo cp -r ~/my-website/* /var/www/my-static-web/ # CÁCH 2: Nếu chưa có, tạo trực tiếp file index.html mẫu có sẵn bằng lệnh Linux: sudo bash -c 'cat << "EOF" > /var/www/my-static-web/index.html <!DOCTYPE html> <html lang="vi"> <head> <meta charset="UTF-8"> <title>Ứng Dụng Web HTML PTIT DevOps</title> <style> body { font-family: sans-serif; text-align: center; padding: 50px; background: #f8fafc; } h1 { color: #2563eb; } p { color: #475569; font-size: 1.1rem; } </style> </head> <body> <h1>🚀 Triển Khai HTML Lên Nginx Thành Công!</h1> <p>File HTML có sẵn trên máy VPS đã được Nginx phục vụ hoàn hảo.</p> </body> </html> EOF' # Kiểm tra lại xem file đã có mặt trong thư mục chưa: ls -la /var/www/my-static-web

Bước 4: Phân quyền sở hữu tệp cho Nginx (www-data)

Đây là bước quan trọng nhất để tránh lỗi 403 Forbidden. Cần cấp quyền sở hữu thư mục cho người dùng hệ thống www-data:

Bash
sudo chown -R www-data:www-data /var/www/my-static-web sudo chmod -R 755 /var/www/my-static-web

Bước 5: Tạo file cấu hình Virtual Host Nginx mới

Tạo file cấu hình tại thư mục sites-available:

Bash
sudo nano /etc/nginx/sites-available/my-static-web.conf

Dán nội dung cấu hình Virtual Host trỏ đúng đường dẫn root /var/www/my-static-web;:

Nginx Virtual Host Config
server { listen 80; server_name _; # Dấu _ chấp nhận mọi tên miền hoặc IP của VPS root /var/www/my-static-web; index index.html index.htm; location / { try_files $uri $uri/ =404; } }

Bước 6: Kích hoạt Virtual Host bằng liên kết mềm (Symbolic Link)

Tạo symlink từ sites-available sang sites-enabled:

Bash
sudo ln -s /etc/nginx/sites-available/my-static-web.conf /etc/nginx/sites-enabled/

Bước 7: Kiểm tra cú pháp an toàn và Reload Nginx

Kiểm tra tính hợp lệ của cú pháp cấu hình trước khi nạp lại dịch vụ:

Bash
sudo nginx -t # Khi thấy output "syntax is ok" và "test is successful", tiến hành reload: sudo systemctl reload nginx

Bước 8: Kiểm tra thành quả truy cập trên trình duyệt

Mở trình duyệt trên máy tính cá nhân gõ địa chỉ IP VPS của bạn: http://<IP_VPS> (ví dụ: http://103.142.25.10). Bạn sẽ thấy nội dung file HTML có sẵn trên VPS được hiển thị hoàn chỉnh!

🛠️ 3.6 Bảng Tra Cứu Khắc Phục Lỗi Nginx Phổ Biến (Troubleshooting)

Mã lỗi HTTP Nguyên nhân thực tế Cách khắc phục dứt điểm
403 Forbidden 1. Nginx không có quyền đọc thư mục root.
2. Trong thư mục không có file index.html và Nginx tắt tính năng duyệt thư mục (autoindex off). 		Chạy lại phân quyền:
sudo chown -R www-data:www-data /var/www/my-app
sudo chmod -R 755 /var/www/my-app
Kiểm tra xem tên file có đúng chính xác là index.html (chữ thường) hay không.
404 Not Found 1. Sai đường dẫn trong directive root.
2. File không tồn tại tại vị trí yêu cầu.
3. Lỗi cấu hình try_files. 		Mở file cấu hình kiểm tra lại directive root /var/www/...; xem đường dẫn có gõ sai chính tả không. Xem log chi tiết bằng: tail -n 20 /var/log/nginx/error.log.
502 Bad Gateway Xảy ra khi cấu hình Reverse Proxy nhưng ứng dụng backend phía sau (NodeJS/Java/Python) chưa được khởi động hoặc bị crash. Kiểm tra backend có đang chạy trên đúng port cấu hình không (ví dụ curl http://localhost:3000).
Nạp config không đổi Quên tạo symlink sang sites-enabled/, hoặc còn file cấu hình mặc định default ghi đè. Xóa file default: sudo rm /etc/nginx/sites-enabled/default rồi reload lại Nginx.

Phần 4: Tường Lửa UFW (Uncomplicated Firewall) Trên Linux VPS

Lá chắn an ninh mạng bảo vệ máy chủ, kiểm soát lưu lượng và mở cổng an toàn cho Nginx

🌐 4.1 Khái Niệm & Vai Trò Của Tường Lửa UFW Trong DevOps

UFW (Uncomplicated Firewall) là công cụ quản lý tường lửa mặc định và phổ biến nhất trên các máy chủ Ubuntu/Debian. Bản chất UFW là một giao diện dòng lệnh thân thiện được xây dựng phía trên iptables phức tạp của nhân hệ điều hành Linux (Linux Kernel Netfilter).

Nguyên tắc mặc định an toàn của UFW:

• Deny incoming: Tự động chặn TẤT CẢ các kết nối từ bên ngoài Internet đi VÀO máy chủ.
• Allow outgoing: Cho phép máy chủ gửi kết nối ĐI RA ngoài bình thường (để cập nhật gói apt, tải mã nguồn).

Vì sao DevOps bắt buộc phải cấu hình UFW:

Ngăn chặn hacker quét cổng (Port Scanning), chống tấn công từ chối dịch vụ (DDoS), bảo vệ các dịch vụ nhạy cảm như MySQL (3306), Redis (6379), MongoDB (27017) không bị truy cập trái phép.

⚡ 4.2 Lệnh Kiểm Tra Trạng Thái & Bật/Tắt Tường Lửa

Terminal: Các lệnh trạng thái UFW
# 1. Kiểm tra trạng thái hiện tại của tường lửa (Status): sudo ufw status # Kết quả có thể là: "Status: inactive" (đang tắt) hoặc "Status: active" (đang bật) # 2. Xem chi tiết trạng thái kèm chính sách mặc định (Verbose): sudo ufw status verbose # 3. Nạp lại cấu hình tường lửa sau khi chỉnh sửa rule: sudo ufw reload # 4. Tạm thời tắt tường lửa khi cần debug kết nối mạng: sudo ufw disable

🚨 4.3 QUY TẮC SỐNG CÒN: Mở Cổng SSH (Port 22) Trước Khi Bật Tường Lửa

⚠️
CẢNH BÁO BỊ KHÓA NGOÀI MÁY CHỦ (LOCKED OUT OF VPS):
Khi bạn gõ sudo ufw enable, nếu bạn CHƯA mở cổng SSH (mặc định là cổng 22), tường lửa sẽ lập tức chặn toàn bộ kết nối SSH đang có! Bạn sẽ bị ngắt kết nối và KHÔNG THỂ SSH VÀO LẠI MÁY CHỦ ĐƯỢC NỮA, chỉ còn cách đăng nhập vào Console nhà cung cấp VPS để khôi phục!
Terminal: Trình tự kích hoạt UFW an toàn tuyệt đối
# BƯỚC 1: Luôn luôn mở cổng SSH TRƯỚC: sudo ufw allow 22/tcp # (Hoặc lệnh tương đương: sudo ufw allow ssh) # BƯỚC 2: Sau khi đã mở port 22 thành công, mới tiến hành BẬT tường lửa: sudo ufw enable # Nhấn 'y' khi terminal hỏi xác nhận: "Command may disrupt existing ssh connections. Proceed with operation (y|n)?"

🔓 4.4 Mở Cổng Dịch Vụ Web Cho Nginx (Port 80, 443 & App Profile)

Để người dùng từ Internet có thể truy cập vào website Nginx của bạn, bạn cần mở cổng giao thức Web tương ứng:

Terminal: Mở cổng Nginx trên UFW
# CÁCH 1: Mở cổng theo số cổng và giao thức: sudo ufw allow 80/tcp # Cho phép truy cập HTTP thông thường sudo ufw allow 443/tcp # Cho phép truy cập bảo mật HTTPS # CÁCH 2 (Khuyên dùng): Sử dụng Application Profile có sẵn của Nginx: # Xem danh sách các ứng dụng được đăng ký với UFW: sudo ufw app list # Sẽ thấy 3 profile của Nginx: # • 'Nginx HTTP' : Chỉ mở cổng 80 # • 'Nginx HTTPS': Chỉ mở cổng 443 # • 'Nginx Full' : Mở CẢ HAI cổng 80 và 443 (Khuyên dùng nhất!) sudo ufw allow 'Nginx Full'

🎯 4.5 Kiểm Soát Truy Cập Theo Địa Chỉ IP (Allow / Deny IP)

Terminal: Lệnh phân quyền IP trên UFW
# 1. Chặn đứng một địa chỉ IP có hành vi tấn công, spam (Blacklist): sudo ufw deny from 192.168.1.150 # 2. Chặn cả một dải mạng IP (Subnet): sudo ufw deny from 192.168.1.0/24 # 3. Chỉ cho phép DUY NHẤT địa chỉ IP của bạn được phép SSH vào cổng 22 (Bảo mật tối đa): sudo ufw allow from 14.161.20.55 to any port 22 proto tcp # 4. Cho phép một server nội bộ truy cập cổng Database MySQL (3306): sudo ufw allow from 10.0.0.5 to any port 3306

🗑️ 4.6 Quản Lý, Xem Danh Sách Đánh Số & Xóa Quy Tắc (Numbered Rules)

Khi muốn xóa một quy tắc đã thêm sai, cách an toàn và chuẩn xác nhất là dùng số thứ tự:

Terminal: Quản lý và xóa rule UFW
# BƯỚC 1: Hiển thị danh sách quy tắc kèm SỐ THỨ TỰ: sudo ufw status numbered # Kết quả mẫu: # To Action From # -- ------ ---- # [ 1] 22/tcp ALLOW IN Anywhere # [ 2] Nginx Full ALLOW IN Anywhere # [ 3] 8080/tcp ALLOW IN Anywhere # BƯỚC 2: Xóa quy tắc theo đúng số thứ tự trong ngoặc vuông (Ví dụ xóa rule số 3): sudo ufw delete 3 # BƯỚC 3: Nếu muốn RESET toàn bộ tường lửa về cài đặt ban đầu của nhà sản xuất: sudo ufw reset
